# Rolltop 开发规划

Rolltop 是一个原创的 macOS 27 菜单栏管理器，功能对标 Bartender，名称、图标、界面均为原创。

- 平台：仅 macOS 27（Golden Gate），Swift 6.4，SwiftUI + AppKit，XcodeGen 生成工程。
- Bundle ID：`com.alphapengwang.rolltop`。原名 Stow，2026-11-25 改名。文中提到的 `tmp/` 证据不入库。非沙盒（Accessibility 在沙盒内不可用）；默认 ad-hoc 签名，也可以用自己的证书（见 README）。
- 平台事实见 [PLATFORM.md](PLATFORM.md)，设计规则见 [DESIGN.md](DESIGN.md)。实现时以这两份为准。
- 时间预算：约 5 小时。到 7.5 小时仍未完成时，砍掉第三波里的"搁架"，不再扩展。

## 1. macOS 27 带来的硬约束

这些是系统限制，Bartender 7 和 Thaw 3 同样受限：

1. 显示/隐藏的粒度是 **App**，不是单个图标。同一个 App 的多个图标只能在同一个分区。
2. 六个系统模块可以单独控制：电池、蓝牙、时钟、声音、Wi-Fi、控制中心。
3. 只要有任何东西被隐藏，隔空投送、专注模式、正在播放、实时活动等系统图标会被 macOS 一并隐藏，无法保留。所以没有东西需要隐藏时，Rolltop 不持有任何限制。
4. App 必须从 `/Applications` 运行，否则被允许了也会被系统隐藏。Rolltop 自己也一样。
5. 隐藏生效时系统不响应时钟点击，Rolltop 需要桥接这次点击才能打开通知中心。

不做的部分及原因：

- **按单个图标隐藏、把一个 App 的图标拆到不同分区**：系统不支持。
- **Bartender 6 的 Live 布局模式（自动移动鼠标拖拽）**：合成 ⌘ 拖拽在 macOS 27 上不可靠。
- **改控制中心的"允许在菜单栏显示"名单来隐藏**：会改动系统自己的设置文件，风险大于收益。
- **"图标变化时显示"触发器（Bartender 的 Show for Updates）**：macOS 27 根本不绘制被隐藏的图标，没有像素可比对，只能观察到少数 App 暴露的辅助功能文字变化，覆盖面太小。
- **AI 代理状态、AirPods 提醒（Top Shelf 的子功能）**：需要专用授权，没有做。
- **自动更新、授权与试用**：没有分发渠道。

第二轮（2026-11-25）补齐了上一版这里列出的小项。其中有三处没有做满：

- **专注模式状态**：公开接口不带受限权利读不到，改由 Rolltop 的 Focus Filter 驱动，只认得加了带预设的 Rolltop 过滤条件的专注模式。
- **天气的地点**只能按名称搜索选择，没有做“使用当前位置”（“使用当前位置”只在自动化的地点条件里有）。
- **iCloud 同步设置**：评估后没有做。键值存储的权利是受限权利，需要 App ID 开通 iCloud 并嵌入描述文件（只能由开发者本人在后台操作），Apple 的文档还写明要求 App Store 分发；单台 Mac 也无法验证跨设备同步。导出/导入备份已经覆盖迁移设置的需要。

## 3. 架构

```
project.yml               XcodeGen 工程定义
Rolltop/
  App/                    入口、AppState（组合根）、FeatureRegistry、CommandRegistry
  Platform/               macOS 27 机制的唯一出口：限制断言（ObjC shim）、AX 读取、
                          系统模块表、时钟桥接、事件合成、权限
  Engine/                 VisibilityEngine、ItemCatalog、ItemActivator、RehideController
  Features/<Name>/        每个功能一个目录，互不引用
  UI/                     共享组件与设计常量
  Resources/              Info.plist、entitlements、Assets、Localizable.xcstrings
Packages/RolltopCore/        纯 Swift 包：模型与决策逻辑，可单测
scripts/                  dev-install.sh、live-lock.sh、mbprobe（诊断）
docs/  tmp/（不入库）
```

关键设计：

- **可见性单位 `OwnerID`**：`.app(bundleID)` 或 `.system(SystemModule)`。布局是 `OwnerID → Section`。
- **白名单是纯函数**：`AllowListPlanner` 输入布局、当前显示状态、临时放行集合、自动化强制显示集合、已知 App 列表，输出"不限制"或"限制（系统 ID 列表 + bundle 列表）"。默认放行，只排除明确要隐藏的。
- **引擎只做应用**：先激活新断言，成功后再作废旧的；代数计数防止迟到回调；任何失败都放开（fail open）。
- **功能之间靠两个注册表解耦**：
  - `CommandRegistry`：每个功能注册命令（id、标题、图标、处理函数）。快捷键、命令面板、URL scheme、Shortcuts 都只认命令 id。
  - `SettingsPane` 贡献：每个功能提供自己的设置页，设置窗口按注册表渲染侧边栏。
- **功能占位**：M1 为所有规划中的功能建好目录和空的 `FeatureModule`，并在 `FeatureRegistry` 里登记。后续代理只填自己的目录，不改共享文件。

**M1a 验收闸门（核心回路，全部实机验证）：**

1. 把一个 App 放进隐藏分区后收起：该图标从菜单栏消失，Rolltop 自己的图标还在。
2. 显示：图标回来。再收起：再次消失。
3. 触发一个隐藏项：临时出现、菜单弹出、菜单关闭后恢复隐藏。
4. 隐藏生效时点击时钟：通知中心能打开。
5. 隐藏生效时启动一个新 App：按默认分区正确显示或隐藏。
6. 正常退出和强制杀掉 Rolltop：菜单栏完整恢复。

每波合并后主会话重新装机、截图验收，再开下一波。

## 5. 风险与对策

| 风险 | 对策 |
|---|---|
| 私有框架接口在系统更新后变化 | 运行时解析并 `@try` 包裹，不可用时保持菜单栏完整并在设置里说明 |
| 在设置里直接排序需要读写系统的布局文件 | 第二轮已实现：只有用户在“设置 › 权限”点了按钮才读取（系统弹框和“选取文件”两条路都做了），写入后在菜单栏里核对，未生效就回滚并如实提示，保留原生 ⌘ 拖拽说明。真实写入已于 2026-11-25 用 `layout-editor.debug-verify-order` 验证生效 |
| 菜单栏只有一条，多个代理同时实机测试会互相干扰 | `scripts/live-lock.sh` 互斥；每次持锁不超过 3 分钟；锁记录实例 PID，过期接管时先杀掉该实例 |
| 从终端启动会继承终端的权限，掩盖真实启动时的权限问题 | 正常启动路径的验收需要用户授予一次辅助功能权限；只在终端启动下验证过的结论标注"未核实" |
| 泄漏的实例会让用户的图标一直隐藏 | 进程退出即自动恢复；所有脚本按 PID 结束自己的实例 |
